## Upgrading Between v3 Releases

Changes between minor releases of v3, such as the value normalization in 3.13, are in [UPGRADING.md](https://github.com/relaticle/custom-fields/blob/3.x/UPGRADING.md). Apply them before you start on 4.0.

## Upgrading to 4.0

4.0 moves record links out of `custom_field_values.json_value` and into a relationship
ledger of their own. It adds two field types beside the Record field you already have. It
also closes every class that is not a documented extension point. This page is the whole
upgrade: what to run and in what order, what your users see, what breaks in your code, and
a checklist to work through.

### Requirements

- **PHP** 8.4+
- **Laravel** 13+
- **Filament** 5+
- The latest 3.x release of Custom Fields, installed and migrated

Laravel 12 hosts stay on 3.x.

Upgrade to the latest 3.x first. The v1-era upgrade script and the 2.x-to-3.x data steps
are gone, so `php artisan custom-fields:upgrade` carries only the steps 4.0 needs. It cannot
catch a host up from further back. If you are still on 2.x, work through
[Upgrading to 3.0](#upgrading-to-30) first.

Value normalization shipped in 3.13: phones store as E.164, and links store lower-cased
with their scheme kept. The latest 3.x already applies it, and 4.0 does not change it.

### ULID and UUID applications: set the key type before you migrate

`database.key_type` sets the keys of every package table a migration creates. It is read at
runtime, so set it before the migrations run. A ULID or UUID application then never
hand-edits a published migration:

```php
// config/custom-fields.php
'database' => [
    // 'bigint', 'ulid', or 'uuid'
    'key_type' => 'ulid',
    // ...
],
```

On a fresh install it shapes all six tables. `tenant_id`, `relationship_id`, and every
polymorphic end follow it. The two relationship slot columns (`from_field_id`,
`to_field_id`) follow your `CustomField` model instead, because they point at it.

On an upgrade, the four tables that predate 4.0 already exist, and no migration changes
their keys. The two new tables follow `key_type`. Leave it at `bigint` on a ULID host and
link inserts fail with a key-type mismatch. Set it in the same change that pulls 4.0 in.

### The upgrade, in order

```bash
composer require relaticle/custom-fields:"^4.0" -W
php artisan vendor:publish --tag="custom-fields-migrations"
php artisan migrate --force
php artisan custom-fields:upgrade --force
```

`migrate` does the whole data change. It creates the two relationship tables. Then
`convert_record_fields_to_relationships` converts every 3.x record field in place:

- The field gets a one-way relationship definition. Its target comes from
  `custom_fields.lookup_type`. The definition is many-to-many where the field allowed
  multiple values, and many-to-one where it did not.
- Each id in the field's `json_value` becomes a link, in the order the array held it, with
  `source = migration`. An id whose row was deleted outright is skipped. An id whose row is
  only soft deleted keeps its link.
- The field's value rows are deleted. Then `custom_fields.lookup_type` is dropped.

A record field that never had a target cannot point anywhere. The migration switches it off
and leaves its value rows in place for you to inspect. The field keeps its `record` type
throughout.

The migration uses the query builder only, so a self-hosted install that runs nothing but
`migrate` on deploy gets the same result. Back up the database first. There is no `down()`.

`custom-fields:upgrade` then checks the schema and clears the package's cached field and
entity metadata. It has two steps, `validate-schema` and `clear-caches`. The 3.x steps are
gone, so a `--skip` value that names one, such as `phone-format`, now fails the command.
`--skip=clear-caches` leaves the cache alone when you would rather forget the keys yourself.
`cache:clear` reaches every key in your cache store.

### New columns

`track_custom_field_values_provenance` adds two nullable columns to `custom_field_values`.
`source` records where the last write came from. `updated_at` records when it happened.
Rows written before the upgrade keep both null. The migration skips a column that already
exists.

A write is stamped `user` unless it runs inside `CustomFields::writing()`, which sets the
source for everything in its callback. Imports through the package's importer stamp
`import`. See [Write context](/essentials/extending#write-context).

The new `custom_field_links` table carries a nullable `metadata` JSON column. Nothing writes
it yet.

### What your users see

#### Three field types where there was one

| Type | Key | What it is |
|---|---|---|
| Record | `record` | The one-way link 3.x already had. Unchanged for users. |
| Relationship | `relationship` | New. A link both entities show, with a field on each end. |
| Status | `status` | New. A single choice whose options carry a workflow category. |

**Record is unchanged.** The field editor asks the same two questions: the entity it points
at, and whether it holds more than one record. The form still renders a searchable select.
What it gains is the ledger underneath. Record columns are now sortable and searchable, and
a force-deleted record takes its links with it. The single-value filter bug is gone with the
storage that hosted it. What it loses is `max_values`, which capped a count the cardinality
now owns.

**Relationship is new.** It configures the cardinality as a sentence between two entity
cards. It names the field that appears on the other entity, and it can be symmetric when the
link reads the same in both directions. It renders records as chips with avatars and a page
to open. Its picker offers to create a record it could not find. Where an end holds a single
record, it confirms a move before taking that record from whoever holds it. Nothing migrates
into it. A record field stays a record field, and 4.0 offers no way to turn one into a
relationship.

**Status is new.** It is a single-choice field whose options each carry a category from a
closed set: `unstarted`, `started`, `completed`, `cancelled`. Reports ask for the completed
options instead of matching the label `Done`. It renders the same input, column, entry and
filter a Select does, and it stores a single option id the same way. Select itself is
unchanged, and no existing field changes type.

A Status field keeps at least one `completed` option. `Rules\RequiresCompletedOption` owns
the rule. The field editor applies it on save, and the migrator applies it in `create()` and
in an `update()` that writes options. See
[Option Categories](/essentials/option-categories#every-status-field-has-a-completed-option)
and [Relationships](/essentials/relationships).

An application that lists its field types in `field_type_configuration->enabled()` gets the
two new types only after adding `relationship` and `status` to that list. An empty list
still means all of them.

#### Redesigned surfaces, with the old views one setting away

Five surfaces have no Filament primitive behind them, so each ships in two presentations of
the same Livewire class. `ui.flavor` is `polished` (the redesigned views, the default) or
`native` (the views those surfaces shipped with before the redesign). `ui.flavor_overrides`
switches a single surface. It accepts only five keys: `relationship-configurator`,
`record-chips`, `record-picker`, `type-picker`, and `attribute-table`.

```php
'ui' => [
    'flavor' => 'polished',

    'flavor_overrides' => [
        // 'attribute-table' => 'native',
    ],
],
```

Only views fork, never the logic underneath. An unknown flavor or override key is rejected
at boot, so a typo fails on the first request instead of quietly reverting a surface. In a
console process it is reported to your log instead, so a bad value never stops `migrate`. A
config published before 4.0 has no `ui` block and gets the defaults. See
[Configuration](/essentials/configuration#ui-flavor).

#### A shorter field form, when you ask for one

The field form is unchanged by default. It opens as a slide-over panel and offers every
setting a field carries. New in 4.0 is `field_form`. It lets a host open the form as a
centered modal and narrow the settings it asks about. The narrowest form asks only for a
type, a name, and whether the field takes more than one value.

```php
'field_form' => [
    'presentation' => 'modal',

    'settings' => ['allow_multiple'],
],
```

Narrowing it removes nothing. A field that already stores `encrypted` or
`unique_per_entity_type` keeps it through an edit. A new field takes the default on
`CustomFieldSettingsData`. See [Configuration](/essentials/configuration#field-form).

#### Pasting a list of options

The options editor can offer a paste action: one option name per line, up to 100 at a time.
Names are trimmed and deduplicated case-insensitively against the names already there. A
200-value vocabulary used to be 200 clicks. The action is off by default. Enable
`CustomFieldsFeature::FIELD_OPTION_PASTE` to show it. See
[Field Types](/essentials/field-types#user-defined-options-default).

#### Emptying a field clears it

A Filament form now dehydrates a field the user emptied, so clearing a multi-value field
through the panel clears it. 3.x withheld the empty state and kept the stored value. No host
action is needed.

A clear travels only on a field the server can prove the form was showing. Some visibility
conditions cannot be reproduced on the server, a model-attribute source among them. A field
behind one keeps its stored value when emptied. That is the fail-safe direction for a
destructive write.

### What breaks in your code

#### Feature flag defaults

Every feature flag is now listed explicitly in `config/custom-fields.php`, on or off, with
the reason for its default. Four flags that were off in 3.x ship on:

| Flag | 3.x | 4.0 | Why |
|---|---|---|---|
| `FIELD_VALIDATION_RULES` | Off | On | Adds the per-field validation editor. A field with no rules configured validates exactly as before. |
| `FIELD_DESCRIPTION_POSITION` | Off | On | Adds an above/below choice to the description that `FIELD_DESCRIPTION` already shows. Unset still renders below. |
| `SECTION_CONDITIONAL_VISIBILITY` | Off | On | The section half of conditional visibility, which was already on for fields. A section with no conditions renders as before. The section modal widens so the conditions row fits. |
| `UI_SECTION_WIDTH_CONTROL` | Off | On | Section width, requested in #181. Sections default to 100%, so nothing moves. One exception: a preset migration that passed a `width` to `CustomFieldSectionData` stored it even with the flag off, and that stored width now applies. |

Seven flags stay off: `FIELD_CODE_AUTO_GENERATE`, `FIELD_OPTION_PASTE`, `FIELD_MULTI_VALUE`,
`FIELD_UNIQUE_VALUE`, `MODEL_ATTRIBUTE_CONDITIONS`, `UI_TOGGLEABLE_COLUMNS_HIDDEN_DEFAULT`, and
`SYSTEM_MULTI_TENANCY`. `FIELD_OPTION_PASTE` is a new editor control a host opts into. Each
of the others changes how existing values are stored, validated, or displayed, so it is the
application's call.

**An unlisted flag now takes the package default.** Your own `features` block still wins for
every flag it names. A flag it does not name reads the shipped default instead of reading as
off. A config published on 3.x therefore inherits the four flips above. Compare your block
against the shipped file when you want the 4.0 answer for a flag you did name.

A config published from a 4.0 development build may name `FIELD_OPTION_CATEGORIES` or
`SYSTEM_RELATIONSHIPS`. Neither case exists any more, and naming one fatals on an undefined
constant, so delete the line. Withhold the `status` type through `field_type_configuration`
if you do not want categorised options at all.

#### Config key renames

`selects.record_lookup` is now `selects.record`. Rename the block in your published config.
The old key is not read.

`management.navigation_group` was a dead key. The package always read
`management.navigation_group_enabled` (default `true`), so setting `navigation_group` had no
effect. Rename it in your published config. If you had set it to `false` to disable the
management page's navigation group, that now takes effect.

#### Relationships are always on

The relationship tables are part of every install, and a record field always keeps its ids
as links. There is no flag for it. An application that wants no record fields disables the
`record` and `relationship` types in `field_type_configuration`.

#### `lookup_type` is gone, and cardinality owns multiplicity

`convert_record_fields_to_relationships` drops `custom_fields.lookup_type`. A record field's
target is one end of its relationship definition, so anything that read the column reads the
definition instead. `CustomField::targetEntityType()` answers from there.
`relationshipDefinitionOrFail()` is what the record column and filter call, because a record
field without a definition is broken after the drop.

`allow_multiple` and `max_values` are ignored for record fields, and the field editor no
longer offers `max_values` there. How many records each end holds is the relationship's
cardinality. The allow-multiple toggle still asks the question, but it writes a cardinality
instead of a setting. Narrowing it later keeps the first record each side is linked to, and
asks before closing the rest.

A record field whose definition is missing renders nothing. The column, the filter, the
entry, and the form field take themselves out of the page. The exception is reported to your
log once per request, naming the field. That is a broken field, not a broken page. Writing
to it throws `RelationshipDefinitionDoesNotExistException`. Delete the field, or give it a
definition with `CreateRelationshipDefinition`.

#### Partial payloads change meaning

A key that is absent from a `custom_fields` payload now leaves a record field's links exactly
as they are. 3.x read an absent key as a clear, and every other field type still does.
Clearing a record field is now explicit: send `[]` or `null`.

Anything that writes a partial payload therefore changes behaviour once `migrate` converts
your record fields. That covers a REST `PATCH`, an AI or chat action, and an import that maps
only some columns. Review those writers before you migrate.

#### Taking a record from its holder

Where the far end of a relationship holds a single record, a payload that would take that
record from another one is rejected, naming the record that holds it. Confirm the
replacement per field by sending `['ids' => [...], 'replace' => true]` where the id list
goes. The plain list stays the default and stays unconfirmed. More than one id for a single
end is rejected as well.

#### Host models that use `UsesCustomFields`

The trait now defines `save(array $options = [])`, so a record and its custom-field writes
land in one transaction. A method your class declares wins over a trait method of the same
name. A model that defines its own `save()` therefore skips the trait's version, and
`parent::save()` reaches Eloquent's, not the trait's. Alias the trait's method and call it:

```php
use UsesCustomFields {
    save as saveWithCustomFields;
}

public function save(array $options = []): bool
{
    // your own logic
    return $this->saveWithCustomFields($options);
}
```

The trait also adds four relations: `outgoingLinks()`, `incomingLinks()`,
`outgoingLinkHistory()` and `incomingLinkHistory()`. Rename any method of yours that uses
one of those names.

#### Preset migrations: the migrator moved, and `lookupType()` is now `target()`

`CustomFieldsMigrator` and `CustomFieldsMigration` left the Filament namespace, because
nothing in them is Filament. No alias keeps the old names. In every preset migration you
still replay, replace:

```text
Relaticle\CustomFields\Filament\Integration\Migrations\  →  Relaticle\CustomFields\Migrations\
->lookupType(                                             →  ->target(
```

`target(string $model, RelationshipCardinality $cardinality = RelationshipCardinality::ManyToOne)`
creates a one-way relationship definition around the field it writes. `allow_multiple` no
longer picks the cardinality. A field that relied on `allow_multiple: true` to hold several
records passes `RelationshipCardinality::ManyToMany`.

`CustomFieldData` loses its `$lookupType` property for the same reason. A preset that passed
it calls `target()` instead. See [Preset Custom Fields](/essentials/preset-custom-fields).

#### Field type capabilities

`FieldSchema` no longer has one setter per capability. A field type passes `FieldCapability`
cases to `capabilities()`. Calls add up, and a repeated case counts once. No capability is
on by default: 3.x made every type searchable and sortable, and 4.0 makes it neither.

```php
// 3.x
return FieldSchema::text()
    ->key('acme-code')
    ->encrypted()
    ->filterable()
    ->allowArbitraryValues();

// 4.0
use Relaticle\CustomFields\Enums\FieldCapability;

return FieldSchema::text()
    ->key('acme-code')
    ->capabilities(
        FieldCapability::Searchable,
        FieldCapability::Sortable,
        FieldCapability::Encryptable,
        FieldCapability::Filterable,
        FieldCapability::AcceptsArbitraryValues,
    );
```

Declare `Searchable` and `Sortable` when your type relied on the old defaults. Leave a case
out where you called `searchable(false)` or `sortable(false)`.

| 3.x `FieldSchema` method | 4.0 `FieldCapability` case |
|---|---|
| `searchable()` | `Searchable` |
| `sortable()` | `Sortable` |
| `filterable()` | `Filterable` |
| `encryptable()`, `encrypted()` | `Encryptable` |
| `withArbitraryValues()`, `allowArbitraryValues()` | `AcceptsArbitraryValues` |
| `withoutUserOptions()` | `WithoutUserOptions` |
| `supportsMultiValue()` | `SupportsMultiValue` |
| `supportsUniqueConstraint()` | `SupportsUniqueConstraint` |
| `systemOnly()` | `SystemOnly` |
| `requiresLookupType()` | `RequiresRelationship` |

The getters `isSearchable()`, `isSortable()`, `isFilterable()`, `isEncryptable()` and
`acceptsArbitraryValues()` are gone too. `longText()` did nothing and is gone. Use
`FieldSchema::text()` for long text.

Two cases are new. The Relationship type declares `SupportsPairing`, which decides whether a
field gets the configurator and the chips. The Status type declares
`CarriesOptionCategories`, which decides whether the options editor asks for a category.
Read the capability, never the type key.

`FieldTypeData` loses its ten boolean properties for one `$capabilities` list. Read a
capability with `supports()`:

```php
// 3.x
$customField->typeData->acceptsArbitraryValues;

// 4.0
$customField->typeData->supports(FieldCapability::AcceptsArbitraryValues);
```

Build `FieldTypeData` through `FieldSchema` only. Its constructor is `@internal`. See
[Field Types](/essentials/field-types#capabilities) for what each case does.

#### Component contracts and bases

The four component contracts moved from `Contracts\` to
`Filament\Integration\Contracts\`, because they return Filament components. Update the `use`
statement.

| 3.x | 4.0 |
|---|---|
| `Contracts\FormComponentInterface` | `Filament\Integration\Contracts\FormComponentInterface` |
| `Contracts\InfolistComponentInterface` | `Filament\Integration\Contracts\InfolistComponentInterface` |
| `Contracts\TableColumnInterface` | `Filament\Integration\Contracts\TableColumnInterface` |
| `Contracts\TableFilterInterface` | `Filament\Integration\Contracts\TableFilterInterface` |

`make()` on each of them gains a `?Illuminate\Database\Eloquent\Model $record = null`
parameter. `TableFilterInterface::make()` also gains `?string $through = null` after it,
which [through relations](/essentials/through-relations) pass down. A component that
implements one of these contracts directly adds the new parameters to its `make()`. So does a
component that extends `AbstractInfolistEntry`, `AbstractTableColumn`, or
`AbstractTableFilter`.

`AbstractFormComponent::make()` is now `final`. A form component implements `create()`, and
may override `transformHydratedValue()`. 3.x let a subclass override `make()`, `configure()`
and `getFieldValidationRules()`. The last two are private now. `applySettingsToComponent()`,
`getCustomFieldOptions()` and `shouldBeSearchable()` stay callable but are `@internal`, and so
are the protected helpers on `AbstractTableFilter`.

`RecordSelectInputComponent` is now `final`. Build a record select on
`AbstractFormComponent` instead. See
[Custom Filament components](/essentials/extending#custom-filament-components).

#### Contract renames and removals

| 3.x | 4.0 |
|---|---|
| `Contracts\ValueResolvers` | `Contracts\ValueResolverInterface` |
| `Contracts\ValidationCapability` | `Contracts\ValidationCapabilityInterface` |
| `Contracts\CustomsFieldsMigrators` | Removed. Type-hint `Migrations\CustomFieldsMigrator`. |
| `Contracts\EntityManagerInterface` | Removed. Type-hint `EntitySystem\EntityManager`. |
| `Contracts\EntityConfigurationInterface` | Removed. Type-hint `EntitySystem\EntityConfigurator`. |

The renamed contracts keep their methods. The three removed contracts each had exactly one
implementation and were never documented extension points. `CustomFieldsMigrator` is now
`final` as well, so a subclass of it no longer compiles. The other two already were.

#### Management form hooks moved to the plugin

3.x registered management form hooks through static methods on the form classes. 4.0
registers them on `CustomFieldsPlugin`, where you add the plugin in your panel provider. Each
hook belongs to that panel's plugin instance, so register it on every panel that shows the
management page. The callbacks take the same arguments as before.

| 3.x | 4.0 |
|---|---|
| `FieldForm::extendSchemaUsing($callback)` | `CustomFieldsPlugin::make()->fieldSchema($callback)` |
| `SectionForm::extendSchemaUsing($callback)` | `CustomFieldsPlugin::make()->sectionSchema($callback)` |
| `FieldForm::resolveUniqueRuleModifierUsing($resolver)` | `CustomFieldsPlugin::make()->uniqueFieldNameRule($resolver)` |
| `FieldForm::resolveUniqueCodeRuleModifierUsing($resolver)` | `CustomFieldsPlugin::make()->uniqueFieldCodeRule($resolver)` |
| `ManageCustomFieldSection::resolveUniqueRuleModifierUsing($resolver)` | `CustomFieldsPlugin::make()->uniqueSectionRule($resolver)` |
| `VisibilityComponent::resolveAvailableFieldsScopeUsing($resolver)` | `CustomFieldsPlugin::make()->visibilityFields($resolver)` |
| `CodeGenerator::resolveUniquenessScopeUsing($callback)` | `CustomFields::scopeCodeUniquenessUsing($callback)` |
| `FieldForm::flushSchemaExtensions()`, `SectionForm::flushSchemaExtensions()` | Removed. Hooks live on the plugin instance. |

```php
// 3.x, in a service provider
FieldForm::extendSchemaUsing(fn (array $schema, ?CustomFieldSection $section): array => [...$schema, $toggle]);

// 4.0, in your panel provider
CustomFieldsPlugin::make()
    ->fieldSchema(fn (array $schema, ?CustomFieldSection $section): array => [...$schema, $toggle]);
```

The 4.0 methods take a `Closure`. 3.x accepted `null` to unregister a hook. Leave the call
out instead. `scopeCodeUniquenessUsing()` is static on `CustomFields`, not on the plugin.
`FormInterface` and `SectionFormInterface` are deleted, and `FieldForm` and `SectionForm` are
`final` and `@internal`. See
[Management form hooks](/essentials/extending#management-form-hooks).

#### Deleted and moved internals

| 3.x | 4.0 |
|---|---|
| `Livewire\Concerns\CreatesCustomFields` | Deleted. Create fields through `CustomFieldsMigrator`, or the model through `CustomFields::newCustomFieldModel()`. |
| `Filament\Management\Schemas\FormInterface` | Deleted. |
| `Filament\Management\Schemas\SectionFormInterface` | Deleted. |
| `Filament\Management\Forms\Components\DateConstraintField` | Moved to `Validation\DateConstraintField`, `@internal`. |
| `TenantContextService::setFromFilamentTenant()` | Removed. Call `TenantContextService::setTenantId(Filament::getTenant()?->getKey())`. |

`getCurrentTenantId()` already falls back to the Filament tenant in a web request, so most
callers of `setFromFilamentTenant()` can drop the call. On `TenantContextService`,
`setTenantResolver()`, `clearTenantResolver()` and `hasTenantContext()` are now `@internal`.
Register a resolver with `CustomFields::resolveTenantUsing()`.

#### Exception rename

`Exceptions\UniqueCustomFieldValueTaken` is now
`Exceptions\UniqueCustomFieldValueTakenException`. Every exception in the package carries
the suffix in 4.0, and an architecture test keeps that true.

The class itself is unchanged. `UsesCustomFields` throws it from its `restoring` hook when a
trashed record gives up a unique value and another record has since taken it. A `catch`
block in a host restore path is the one place that needs the new name.

```php
// 3.x
use Relaticle\CustomFields\Exceptions\UniqueCustomFieldValueTaken;

// 4.0
use Relaticle\CustomFields\Exceptions\UniqueCustomFieldValueTakenException;
```

#### Translation keys

An application that publishes the package's language files checks one removed key and one
new one:

- `custom-fields::custom-fields.field.form.lookup_type.label` is gone. Delete it from your
  override.
- `custom-fields::custom-fields.validation.status_requires_completed_option` is new. It is the
  message `RequiresCompletedOption` fails with, and it takes a `:category` placeholder.

Laravel merges a published override over the package file, so the other new keys fall back
to English until you translate them.

#### Static analysis

`new*Model()` on `CustomFields`, such as `newCustomFieldModel()`, now returns the model type
instead of `mixed`. `use*Model()` takes a `class-string` of that model. The `*Model()`
getters return `class-string<...>`, as in 3.x. PHPStan may now report code that relied on
`mixed`, such as a call to a method your subclass adds. Narrow the type with an `instanceof`
check or a `@var` annotation.

#### Classes are final, and `@internal` is not covered by semver

Every class under `src/` is now `final` except the documented extension points.
Inheritance is no longer a supported way to change package internals. The seams that stay
open are listed on [Extending](/essentials/extending). They include `BaseFieldType` and most
shipped field-type definitions, the `Abstract*` component bases, `CustomFieldsMigration`, the
six swappable models and their query builder, the management page, the contracts, and the
model and page traits.

Everything else is closed: services, factories, resolvers, builders, data objects,
exceptions, observers, scopes, middleware, facades, the management form schemas, and the
Livewire components. If you subclassed one of those, it no longer compiles. Move to the seam
that covers your case, or open an issue for a new seam.

`final` stops subclassing, not calling. The
[Public API](/essentials/extending#public-api) section lists the classes 4.x keeps stable.
Anything tagged `@internal`, a class or a single method, may change in any 4.x release.
Check every package class your code calls against that list.

### MySQL and the duplicate-edge guard

Duplicate open edges are blocked by a partial unique index. PostgreSQL and SQLite support
one, and the MySQL family does not. The link writer enforces the same rule on every driver
inside its transaction, so nothing is missing functionally. A MySQL host that wants the
database-level guard as well can add it with a generated column:

```sql
ALTER TABLE custom_field_links
    ADD COLUMN active_edge_key VARCHAR(512)
        GENERATED ALWAYS AS (
            IF(active_until IS NULL,
               CONCAT_WS('|', relationship_id, from_entity_type, from_entity_id,
                              to_entity_type, to_entity_id),
               NULL)
        ) STORED,
    ADD UNIQUE INDEX cf_links_active_edge_unique (active_edge_key);
```

The column is NULL for a closed edge. MySQL treats NULLs in a unique index as distinct, so
history never collides with the edges that are open.

### 4.0 Checklist

Before you upgrade:

- [ ] Back up your database.
- [ ] Verify PHP 8.4+, Laravel 13+, Filament 5+, and the latest 3.x release installed.
- [ ] Set `database.key_type` if your application uses ULID or UUID keys.
- [ ] Review every writer that sends a partial `custom_fields` payload. An absent record-field key stops meaning "clear".

Configuration:

- [ ] Compare your `features` block against the shipped file. Unlisted flags now take the package default.
- [ ] Delete `FIELD_OPTION_CATEGORIES` or `SYSTEM_RELATIONSHIPS` from a config published from a 4.0 development build.
- [ ] Rename `selects.record_lookup` to `selects.record` and `management.navigation_group` to `management.navigation_group_enabled`.
- [ ] Add `relationship` and `status` to `field_type_configuration->enabled()` if you list your types explicitly.
- [ ] Remove `field.form.lookup_type.label` from published language files.

Code:

- [ ] Give any model that overrides `save()` an alias for the trait's `save()`, and rename methods that clash with the four link relations.

## Picking Up New Migrations

Package migrations are not run automatically by `php artisan migrate` after a version bump.
They are only copied into your app on first install, or when you explicitly republish them:

```bash
php artisan vendor:publish --tag="custom-fields-migrations"
php artisan migrate
```

For example, a release may relax the `custom_fields` unique key from
`(code, entity_type[, tenant])` to `(code, entity_type[, tenant], custom_field_section_id)`
so a field code can be reused across different sections, the shape `onlySections()` (see
[Builder Scoping](/essentials/builder-scoping)) relies on. Existing installs need the
republish-and-migrate step above to pick that change up; it is not applied automatically.

Package migrations are up-only and ship without a `down()` method; there is no supported
way to roll one back. If you need to reverse a widened unique key by hand, resolve any
rows that ended up sharing a code across sections first, then drop the wide index and
recreate the narrow one yourself.

**NULL is not unique-constrained.** `custom_field_section_id` is nullable, and both MySQL
and Postgres treat `NULL` as distinct from every other value in a unique index, including
one that includes it. So after this migration, two sectionless fields
(`custom_field_section_id IS NULL`) can still share a code for the same entity type, a
collision the narrow key used to prevent. There is no schema-level fix for this; keep
sectionless codes unique at the application layer if you rely on that guarantee.

## Upgrading to 3.0

### Requirements

Custom Fields v3 requires:

- **PHP** 8.3+
- **Laravel** 12+
- **Filament** 5.0+

### Quick Upgrade

```bash
composer require relaticle/custom-fields:"^3.0" -W
php artisan migrate
php artisan custom-fields:upgrade
```

The v3 upgrade command handled data migrations for phone fields, email fields, and lookup
fields automatically.

### Breaking Changes

#### High Impact

##### Filament 5 Required

Custom Fields v3 requires Filament 5. If you're still on Filament 4, upgrade Filament first following the [Filament upgrade guide](https://filamentphp.com/docs/5.x/upgrade-guide).

##### Lookup Fields Removed from Non-Record Types

The `lookup_type` setting was removed from field types that don't support entity lookups. The v3 upgrade command migrated affected fields automatically.

**Affected field types**: Text, Textarea, Number, Date, DateTime, Email, Phone, and other non-relational types.

If you were using `lookup_type` on these fields, they were converted to standard fields.

#### Medium Impact

##### Phone Field Format Changed

Phone fields now store values as JSON arrays of E.164 strings (supporting multiple phone numbers):

```php
// v2 format (single string in string_value column)
"+11234567890"

// v3 format (JSON array in json_value column)
["+11234567890"]
```

The v3 upgrade command migrated existing phone values automatically.

##### Email Field Format Changed

Email fields now support multiple values stored as JSON:

```php
// v2 format (string)
"user@example.com"

// v3 format (JSON array)
["user@example.com"]
```

The v3 upgrade command migrated existing email values automatically.

#### Low Impact

##### New Phone Validation Package

v3 added `propaganistas/laravel-phone` for phone validation. This is installed automatically with composer.
